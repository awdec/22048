<h1><center>第三节 TCP</center></h1>

## 1. TCP 的特点

TCP 提供面向连接、可靠、按序、无重复的全双工字节流服务。每条 TCP 连接只有两个端点，不能直接用于一对多或广播通信。

TCP 面向字节流，不保留应用层报文边界。发送端可以把应用数据划分为不同大小的报文段，接收端按序恢复连续字节流。

## 2. TCP 报文段首部

关键字段包括：

- 源端口和目的端口。
- 序号与确认号。
- 数据偏移。
- 控制位 SYN、ACK、FIN、RST、PSH、URG。
- 接收窗口。
- 校验和、紧急指针和选项。

没有选项时，TCP 首部长度为 20 字节。

## 3. 序号与确认号

TCP 按字节编号。报文段序号是本段数据第一个字节的序号；确认号表示期望收到的下一个字节序号，是累计确认。

若报文段序号为 $x$，携带 $L$ 字节数据，则正确接收后确认号为：

$$
x+L.
$$

SYN 和 FIN 虽然不携带普通数据，也各消耗一个序号；纯 ACK 且不携带数据时通常不消耗序号。

## 4. 可靠传输机制

TCP 综合使用以下机制实现可靠传输：

- 校验和检测差错。
- 序号识别丢失、重复与失序。
- ACK 累计确认。
- 接收缓存与按序交付。
- 超时重传。
- 快速重传。

发送方连续收到 3 个对同一数据的重复 ACK 时，通常不等待计时器超时，而是立即重传推测丢失的报文段。

## 5. 超时重传

TCP 根据测得的 RTT 动态估计重传超时 RTO。RTO 应略大于平滑 RTT，并结合 RTT 的变化程度调整。

重传报文段收到 ACK 时，发送方难以判断 ACK 对应原报文还是重传报文，因此 Karn 算法通常不使用这种样本直接更新 RTT。

## 6. TCP 流量控制

接收方在 TCP 首部中通告接收窗口 `rwnd`，限制发送方未确认数据量，避免接收缓冲区溢出。

允许发送方保留在途且尚未确认的数据量上限同时受接收窗口和拥塞窗口限制：

$$
\text{有效窗口上限}=\min(\text{rwnd},\text{cwnd}).
$$

若当前在途未确认数据量为 `FlightSize`，则当前还能发送的数据量至多为：

$$
\max\left(0,\min(\text{rwnd},\text{cwnd})-\text{FlightSize}\right).
$$

接收方可以通告零窗口暂停发送。为防止窗口更新报文丢失造成永久等待，发送方使用持续计时器发送零窗口探测。

## 7. TCP 拥塞控制

经典 TCP 拥塞控制包含慢开始、拥塞避免、快重传和快恢复：

- **慢开始**：拥塞窗口从较小值开始，通常按 RTT 近似指数增长。
- **拥塞避免**：达到慢开始门限后，拥塞窗口通常按 RTT 线性增长。
- **超时**：通常表示严重拥塞，将门限减半并把拥塞窗口降到较小初值。
- **三个重复 ACK**：执行快重传，并通常进入快恢复，不必把拥塞窗口降到最小。

具体窗口变化取决于 TCP 版本和题目给出的规则。

## 8. 三次握手

假设客户端初始序号为 $x$，服务器初始序号为 $y$：

1. 客户端发送 `SYN=1, seq=x`。
2. 服务器发送 `SYN=1, ACK=1, seq=y, ack=x+1`。
3. 客户端发送 `ACK=1, seq=x+1, ack=y+1`。

三次握手确认双方收发能力，并避免过期连接请求导致服务器错误建立连接。第三次握手可以携带数据。

## 9. 四次挥手与 TIME-WAIT

TCP 是全双工的，两个方向需要分别关闭。主动关闭方发送 FIN，被动方先确认，待剩余数据发送完后再发送自己的 FIN，主动方最后确认。

主动关闭方进入 TIME-WAIT 并等待 $2MSL$：

- 保证最后 ACK 丢失时可以重发。
- 让旧连接中滞留的报文在网络中消失，避免影响相同四元组的新连接。

ACK 与 FIN 有时可以合并，因此实际报文数量不一定机械地总是四个。

::: warning 易错点
TCP 序号按字节而不是按报文段递增；实际发送窗口取 `rwnd` 与 `cwnd` 的较小值，再扣除已经发送但尚未确认的数据。
:::
