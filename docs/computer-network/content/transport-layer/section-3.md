<h1><center>第三节 TCP</center></h1>

传输控制协议 TCP 在不可靠的 IP 服务之上，为应用进程提供面向连接的可靠传输。本节的核心是根据 TCP 首部理解序号、确认号和窗口，再把这些字段与连接管理、可靠传输、流量控制和拥塞控制联系起来。

## 1. TCP 的特点

### 1.1 面向连接

TCP 在传输数据前必须建立连接，通信过程中维护连接状态，数据传输结束后再释放连接。TCP 连接是一条由两个端系统维护的**逻辑连接**，并不是独占链路带宽的物理连接。

一个 TCP 连接由通信双方的套接字地址确定，通常表示为四元组：

$$
(\text{源 IP 地址},\text{源端口号},\text{目的 IP 地址},\text{目的端口号}).
$$

服务器可以在同一端口上同时维持多个 TCP 连接，只要连接的四元组不同即可区分。

### 1.2 点对点和全双工

每条 TCP 连接只有两个端点，只能进行一对一通信，不能直接用于一对多、多播或广播通信。

TCP 提供全双工通信。连接建立后，双方都可以同时发送和接收数据，并分别维护各自方向上的发送序号、确认号、发送缓存和接收缓存。一个方向停止发送，不代表另一个方向也必须立即停止。

### 1.3 可靠、按序、无重复交付

TCP 综合使用检验和、序号、确认、计时器、重传和滑动窗口等机制，使接收方应用进程获得可靠、按序、无重复的字节流。这里的可靠性由通信端系统实现，中间路由器无须保存每条 TCP 连接的可靠传输状态。

### 1.4 面向字节流

TCP 把应用层交付的数据看成连续、无结构的字节流，不保留应用层报文边界。发送方应用一次写入的数据，可能被 TCP 拆到多个报文段中；多次写入的数据也可能合并到同一个报文段中。

```text
应用写入：  [报文 A][报文 B]
TCP 字节流：[................]
实际分段：  [段 1][   段 2   ][段 3]
```

接收方 TCP 按序恢复字节流，但应用层必须自行确定消息边界，例如使用固定长度、分隔符或长度字段。

### 1.5 TCP 的其他特点

- TCP 首部至少为 20 B，比 UDP 首部复杂。
- TCP 使用累计确认，确认号表示接收方期望收到的下一个字节序号。
- TCP 同时提供流量控制和拥塞控制，分别保护接收端与网络。
- TCP 根据网络状态动态调整发送行为，不保证固定带宽、固定时延或固定报文段大小。

::: warning 易错点
TCP 的“面向连接”不等于电路交换，“面向字节流”不等于按应用报文交付。TCP 保证字节流可靠、按序到达，但不替应用层保存消息边界。
:::

## 2. TCP 报文段

TCP 报文段由 TCP 首部和数据部分组成。首部中的端口号用于复用与分用，序号和确认号用于可靠传输，窗口字段用于流量控制，控制位用于连接管理。

### 2.1 TCP 首部格式

按照 408 常用的经典格式，TCP 基本首部如下：

```text
  0               15 16              31
 +------------------+------------------+
 |      源端口       |      目的端口      |
 +------------------+------------------+
 |                序号                 |
 +------------------------------------+
 |               确认号                 |
 +----+------+--------------------------+
 |首部| 保留 |URG ACK PSH RST SYN FIN   |
 |长度|      |        窗口               |
 +------------------+------------------+
 |      检验和       |      紧急指针      |
 +------------------+------------------+
 |        选项（长度可变）和填充          |
 +------------------------------------+
 |                 数据                |
 +------------------------------------+
```

| 字段 | 长度 | 作用 |
| --- | --- | --- |
| 源端口、目的端口 | 各 16 bit | 标识发送和接收应用的端口 |
| 序号 | 32 bit | 本报文段所发送数据的第一个字节的序号 |
| 确认号 | 32 bit | 期望收到对方的下一个字节序号，仅在 ACK=1 时有效 |
| 数据偏移 | 4 bit | 表示 TCP 首部长度，单位是 4 B，也称首部长度 |
| 控制位 | 各 1 bit | 控制连接建立、确认、复位、释放等操作 |
| 窗口 | 16 bit | 通告本方当前愿意接收的数据量 |
| 检验和 | 16 bit | 检测伪首部、TCP 首部和数据中的比特差错 |
| 紧急指针 | 16 bit | 在 URG=1 时与序号配合标识紧急数据的位置 |
| 选项和填充 | 长度可变 | 携带 MSS 等选项，并补齐为 4 B 的整数倍；窗口扩大、时间戳和选择确认许可属于拓展了解内容 |

数据偏移字段的最小值为 5，表示 $5\times4=20\text{ B}$；最大值为 15，表示 $15\times4=60\text{ B}$。因此 TCP 首部长度范围为 20～60 B。

### 2.2 序号与确认号

TCP 对一个方向上发送的每个数据字节编号。若某报文段的序号为 $x$，携带 $L$ 字节数据，则该报文段覆盖的字节序号为：

$$
x,x+1,\ldots,x+L-1.
$$

接收方正确收到这些连续字节后，返回的累计确认号为：

$$
\operatorname{ack}=x+L.
$$

确认号 $n$ 表示序号小于 $n$ 的所有连续字节已经收到，下一步期望收到序号为 $n$ 的字节。它不是“已经收到的最后一个字节序号”。

SYN 和 FIN 即使不携带普通数据，也各消耗一个序号；不携带数据的纯 ACK 通常不消耗序号。一般可以写成：

$$
\text{下一序号}=\operatorname{seq}+\text{数据长度}+[\mathrm{SYN}]+[\mathrm{FIN}],
$$

其中控制位存在时对应方括号取 1，否则取 0。序号字段为 32 bit，计算到最大值后按模 $2^{32}$ 回绕。

### 2.3 控制位

| 控制位 | 含义 |
| --- | --- |
| URG | 紧急指针有效 |
| ACK | 确认号字段有效；连接建立后通常置 1 |
| PSH | 希望接收方尽快把数据交付给应用进程 |
| RST | 复位异常连接或拒绝无效连接请求 |
| SYN | 同步初始序号，用于建立连接 |
| FIN | 发送方数据已经发送完毕，请求关闭本方向的数据流 |

控制位可以组合出现。例如，服务器的第二次握手通常同时置 `SYN=1, ACK=1`；连接释放期间的报文通常同时携带 `FIN=1, ACK=1`。

### 2.4 窗口、检验和与选项

TCP 首部中的窗口字段是报文发送方根据自身接收缓存情况通告的**接收窗口**。它限制对方允许保留的未确认数据量，用于流量控制；它不是拥塞窗口，首部中也不存在直接传输拥塞窗口的字段。

TCP 检验和的计算方法与 UDP 类似，覆盖 IP 伪首部、TCP 首部和 TCP 数据。发送端计算时把检验和字段置 0，接收端把收到的检验和一起进行 16 bit 反码求和。TCP 检验和必须使用，但只能检错，不能纠错或自动重传。

最大报文段长度 MSS 表示一个 TCP 报文段中允许携带的最大数据量，不包括 TCP 首部和 IP 首部。若已知路径 MTU，则一个报文段能够携带的最大 TCP 数据量为：

$$
\mathrm{MSS}_{\max}=\text{路径 MTU}-\text{IP 首部长度}-\text{TCP 首部长度}.
$$

发送方实际采用的 MSS 可以小于上述上限。例如，路径 MTU 为 1500 B 时：

- 使用无选项的 20 B IPv4 首部和 20 B TCP 首部，最大 TCP 数据量为 1460 B。
- 使用无扩展首部的 40 B IPv6 基本首部和 20 B TCP 首部，最大 TCP 数据量为 1440 B。

MSS 选项只能出现在带 SYN 的报文段中。连接建立时，双方分别通告本方能够接收的最大报文段数据长度，两个方向通告的 MSS 可以不同；一端的实际发送 MSS 还要受到对方通告值和本地 IP 层允许发送尺寸的共同限制。因此，MSS 不是双方必然协商成同一个值，也不能与 MTU 或整个 TCP 报文段长度混淆。

::: tip 首部题顺序
先用数据偏移求首部长度，再用 IP 总长度减去 IP 首部与 TCP 首部求数据长度；最后根据数据长度及 SYN、FIN 是否置位计算下一序号和确认号。
:::

## 3. TCP 连接管理

TCP 连接管理包括连接建立、数据传输状态维护和连接释放。连接的两个方向具有各自的序号空间，因此双方都要向对方通告并确认初始序号。

### 3.1 三次握手

假设客户端选择初始序号 $x$，服务器选择初始序号 $y$，典型建立过程如下：

1. **第一次握手**：客户端发送 `SYN=1, seq=x`，然后进入 `SYN-SENT` 状态。SYN 消耗一个序号。
2. **第二次握手**：服务器发送 `SYN=1, ACK=1, seq=y, ack=x+1`，然后进入 `SYN-RECEIVED` 状态。该报文既确认客户端的 SYN，也通告服务器的初始序号。
3. **第三次握手**：客户端发送 `ACK=1, seq=x+1, ack=y+1`，进入 `ESTABLISHED` 状态；服务器收到后也进入 `ESTABLISHED` 状态。

```text
客户端                                      服务器
  | ---- SYN=1, seq=x ----------------------> |
  | <--- SYN=1, ACK=1, seq=y, ack=x+1 ------- |
  | ---- ACK=1, seq=x+1, ack=y+1 -----------> |
  |              连接建立                     |
```

第三次握手的纯 ACK 不消耗序号，因此如果它不携带数据，客户端随后发送数据时仍可从 `seq=x+1` 开始；第三次握手也可以携带数据，此时序号要按实际数据长度继续推进。

三次握手的主要作用是：

- 让双方交换并确认彼此的初始序号。
- 确认双方方向上的报文能够到达，并具备建立连接的条件。
- 防止网络中滞留的旧连接请求使服务器错误地建立连接。

仅进行两次握手时，服务器无法确认自己的 SYN 和初始序号是否已经被客户端接收，也更容易受失效连接请求影响，因此 TCP 使用三次握手。

### 3.2 四次挥手

TCP 是全双工的，两个方向的数据流需要分别关闭。假设主机 A 主动关闭，A 当前下一发送序号为 $u$；主机 B 当前下一发送序号为 $v$，之后又发送了一些数据，使发送 FIN 时的序号为 $w$：

1. A 发送 `FIN=1, ACK=1, seq=u, ack=v`，进入 `FIN-WAIT-1`。FIN 消耗一个序号。
2. B 返回 `ACK=1, seq=v, ack=u+1`，进入 `CLOSE-WAIT`；A 收到后进入 `FIN-WAIT-2`。此时 A 到 B 的方向已经关闭，但 B 仍可继续向 A 发送数据，这称为半关闭。
3. B 发送完剩余数据后，发送 `FIN=1, ACK=1, seq=w, ack=u+1`，进入 `LAST-ACK`。
4. A 返回 `ACK=1, seq=u+1, ack=w+1`，进入 `TIME-WAIT`；B 收到该 ACK 后关闭连接。

```text
主动关闭方 A                                  被动关闭方 B
  | ---- FIN, seq=u --------------------------> |
  | <--- ACK, ack=u+1 ------------------------- |
  | <--- FIN, seq=w ---------------------------- |
  | ---- ACK, ack=w+1 -------------------------> |
  |       TIME-WAIT              CLOSED          |
```

收到对方 FIN 后，本方可能还有数据没有发送完，因此对 FIN 的 ACK 和本方的 FIN 通常分开发送，形成四次交互。如果本方已经没有剩余数据，ACK 和 FIN 可以合并，所以实际报文数量不一定始终是四个。

### 3.3 TIME-WAIT

主动关闭方在发送最后一个 ACK 后通常等待 $2\mathrm{MSL}$，再进入 `CLOSED` 状态。MSL 是报文段最大生存时间。

等待 $2\mathrm{MSL}$ 有两个主要作用：

1. 如果最后一个 ACK 丢失，被动关闭方会重传 FIN，主动关闭方仍能收到并再次发送 ACK。
2. 让本连接中可能滞留的旧报文段在网络中消失，避免它们影响随后建立的相同四元组连接。

`TIME-WAIT` 通常出现在主动关闭方；被动关闭方等待应用关闭的状态是 `CLOSE-WAIT`，二者不能混淆。

### 3.4 连接复位（拓展了解）

RST 用于异常终止或拒绝连接。例如，报文到达不存在的连接、目的端口没有进程监听，或应用要求立即中止连接时，可以发送 RST。复位与 FIN 的有序关闭不同，通常不保证剩余数据继续交付。

::: warning 易错点
SYN 和 FIN 各消耗一个序号，纯 ACK 通常不消耗序号；三次握手是建立一条双向逻辑连接，四次挥手则是分别关闭两个方向的数据流。
:::

## 4. TCP 可靠传输

TCP 的可靠传输不是由某个单独机制完成的，而是检验和、序号、确认、重传、缓存和滑动窗口共同作用的结果。

### 4.1 序号、累计确认与接收缓存

TCP 使用序号识别数据的次序、重复和缺失。接收方通常采用累计确认：确认号 $n$ 表示序号小于 $n$ 的连续字节已经正确收到。

例如，发送方依次发送三个报文段：

```text
段 1：seq=1001，数据 500 B
段 2：seq=1501，数据 500 B   ← 丢失
段 3：seq=2001，数据 500 B   ← 到达
```

接收方收到段 1 后确认 `ack=1501`。即使随后收到失序的段 3，由于从 1501 开始仍存在字节流空洞，累计确认号通常仍为 1501，由此产生重复 ACK。接收方是否暂存失序数据取决于实现，但不能越过缺口向应用层交付连续字节流。

若收到重复报文段，接收方可以根据序号识别并丢弃重复数据，同时重新发送累计确认，避免应用层收到重复字节。

### 4.2 滑动窗口

TCP 允许发送方在未收到前一个报文段确认时继续发送后续数据，从而使多个报文段同时处于网络中，提高链路利用率。

发送窗口中的字节可以分为：

```text
已经确认 | 已发送未确认 | 允许发送但尚未发送 | 暂不允许发送
          <----------- 发送窗口 ----------->
```

当较小序号的数据得到累计确认后，窗口左边界向右移动，发送方可以发送新的数据。TCP 的窗口和序号按**字节**计算，不是按报文段数量计算。

### 4.3 超时重传

发送方为已发送但尚未确认的数据设置重传计时器。若在重传超时时间 RTO 内没有收到相应确认，就重传最早未确认的数据。

RTO 需要根据往返时间 RTT 动态估计：

- RTO 过小会造成不必要的重复重传。
- RTO 过大会使真正丢包后的恢复过慢。
- TCP 通常对 RTT 样本进行平滑，并结合 RTT 波动程度设置 RTO。
- 发生连续超时时，RTO 通常采用指数退避，以免拥塞时频繁重传。

重传报文段的确认可能对应原报文段，也可能对应重传报文段，发送方难以判断。作为拓展了解，Karn 算法不使用存在重传歧义的样本更新 RTT，而是在后续没有歧义的传输中继续测量。

### 4.4 快重传

若某个报文段丢失，而它后面的报文段继续到达，接收方会反复确认当前缺口开始处的序号。发送方连续收到 **3 个重复 ACK** 后，通常认为相应报文段已经丢失，不等待 RTO 到期，立即执行快重传。

重复 ACK 本身不会推进累计确认号；“3 个重复 ACK”是指在最初那个 ACK 之外，又连续收到三个具有相同确认号的 ACK。

超时重传和快重传都用于恢复丢失数据，但超时通常被视为更严重的拥塞信号；快重传还能触发后续的快恢复处理。

### 4.5 TCP 可靠传输的边界

TCP 的检验和负责检错，序号和确认用于判断数据状态，重传负责恢复丢失或出错的数据。任何单一机制都不能独立完成可靠传输：

- 只有检验和，不能恢复已经损坏或丢失的数据。
- 只有序号，不能确认接收方是否真正收到数据。
- 只有确认而没有计时器，确认丢失时可能永久等待。

TCP 向应用层保证可靠字节流，但无法保证实时到达，也无法保证某次应用写入恰好对应一次接收操作。

::: tip 可靠传输题
先根据序号和数据长度确定每段覆盖的字节范围，再找出接收方当前连续收到的最大范围。累计确认号始终指向第一个尚未连续收到的字节。
:::

## 5. TCP 流量控制

流量控制用于避免发送方发送过快，导致接收方来不及处理、接收缓存溢出。控制依据是接收方通告的接收窗口 `rwnd`。

### 5.1 接收窗口

接收方根据接收缓存中的可用空间，在 TCP 首部的窗口字段中通告 `rwnd`。可以把其基本关系理解为：

$$
\mathrm{rwnd}=\text{接收缓存容量}-\text{尚未被应用读取的已接收数据量}.
$$

发送方在途且尚未确认的数据不能超过接收方通告的窗口。随着接收方应用读取数据、缓存空间增大，接收方可以在后续 ACK 中通告更大的窗口。

窗口通告是动态的，并与确认号共同确定发送方可以使用的字节范围。它反映的是接收端能力，不直接反映网络是否拥塞。

### 5.2 实际发送窗口

发送方还要受拥塞窗口 `cwnd` 限制，因此允许保留在途数据的窗口上限为：

$$
\text{发送窗口上限}=\min(\mathrm{rwnd},\mathrm{cwnd}).
$$

若当前已经发送但尚未确认的数据量为 `FlightSize`，则当前还能继续发送的数据量至多为：

$$
\max\left(0,\min(\mathrm{rwnd},\mathrm{cwnd})-\mathrm{FlightSize}\right).
$$

例如，若 `rwnd=12 KB`、`cwnd=8 KB`，已有 `3 KB` 数据在途，则发送窗口上限为 `8 KB`，当前最多还能发送 `5 KB`。

### 5.3 零窗口与持续计时器

当接收缓存没有可用空间时，接收方可以通告 `rwnd=0`，发送方暂停发送普通数据。之后接收方应用读取数据，可以发送窗口更新报文。

如果窗口更新报文丢失，接收方等待新数据，发送方又因零窗口等待更新，双方可能永久等待。为避免这种情况，发送方启动**持续计时器**，到期后发送零窗口探测报文，促使接收方重新通告当前窗口。

零窗口探测是为了解决窗口更新丢失造成的死锁，不是拥塞控制中的重传计时器。

### 5.4 流量控制与拥塞控制的区别

| 对比项 | 流量控制 | 拥塞控制 |
| --- | --- | --- |
| 保护对象 | 接收方及其接收缓存 | 整个网络 |
| 主要依据 | 接收窗口 `rwnd` | 拥塞窗口 `cwnd`、丢包或其他拥塞信号 |
| 信息来源 | 接收方在 TCP 首部中通告 | 发送方根据网络反馈维护 |
| 典型问题 | 接收方来不及处理 | 网络负载过大、路由器排队或丢包 |

::: warning 易错点
TCP 首部的窗口字段携带的是 `rwnd`，不是 `cwnd`；发送方真正可用的窗口同时受二者限制，计算还能发送多少时还必须扣除在途未确认数据。
:::

## 6. TCP 拥塞控制

拥塞是指网络负载超过可用资源的处理能力，引起排队时延增大、路由器缓冲区溢出、分组丢失，严重时甚至使有效吞吐量下降。TCP 发送方通过拥塞窗口 `cwnd` 控制注入网络的未确认数据量。

### 6.1 基本变量与判断

- **拥塞窗口 `cwnd`**：由发送方维护，反映发送方根据网络状况估计的可用容量。
- **慢开始门限 `ssthresh`**：决定采用慢开始还是拥塞避免的阈值。
- **最大报文段长度 MSS**：拥塞窗口在题目中经常以 MSS 为单位。
- **在途数据量 `FlightSize`**：已经发送但尚未确认的数据量。

实际发送仍要同时满足：

$$
\mathrm{FlightSize}\leq\min(\mathrm{rwnd},\mathrm{cwnd}).
$$

经典拥塞控制包含慢开始、拥塞避免、快重传和快恢复。具体初始窗口和丢包后的数值处理可能随 TCP 版本而异，计算题应优先采用题目给定规则；未特别说明时，通常采用教材中的经典模型。

::: info 标准规则与 408 经典模型
408 经典计算通常假设初始 `cwnd=1 MSS`，在 `cwnd` 达到 `ssthresh` 后转入拥塞避免，并在检测到拥塞时把 `ssthresh` 简化为当前 `cwnd` 的一半。RFC 5681 允许 `cwnd=ssthresh` 时选择慢开始或拥塞避免；首次由重传计时器检测到相应丢失时，要求 `ssthresh` 不大于 $\max(\mathrm{FlightSize}/2,2\mathrm{SMSS})$，其中 SMSS 表示发送方最大报文段长度。做题时应以题目给出的初始窗口、门限和版本规则为准。
:::

### 6.2 慢开始

在经典模型中，`cwnd` 从较小值开始，常按 `1 MSS` 计算。慢开始期间，每收到一个对新数据的 ACK，`cwnd` 通常增加 `1 MSS`。一个窗口的数据都得到确认后，`cwnd` 在一个 RTT 内近似翻倍：

$$
1\rightarrow2\rightarrow4\rightarrow8\rightarrow\cdots\quad(\mathrm{MSS}).
$$

当 `cwnd` 达到 `ssthresh` 后，转入拥塞避免。慢开始的“慢”是相对于一开始就发送大量数据而言；它的窗口增长实际上是指数级的。

### 6.3 拥塞避免

拥塞避免采用加法增大。经典模型中，每经过一个 RTT，`cwnd` 约增加 `1 MSS`：

$$
8\rightarrow9\rightarrow10\rightarrow11\rightarrow\cdots\quad(\mathrm{MSS}).
$$

实现时可以在每收到一个新 ACK 后做小幅增加，使一个 RTT 内的总增量接近 `1 MSS`。因此：

- 慢开始阶段近似按 RTT 指数增长。
- 拥塞避免阶段近似按 RTT 线性增长。

### 6.4 超时后的处理

重传计时器超时通常表示网络拥塞较严重。在 408 常用的经典模型中：

1. 把 `ssthresh` 设置为发生拥塞时窗口的一半，具体取整方式按题目规定。
2. 把 `cwnd` 重新设置为较小初值，经典题通常取 `1 MSS`。
3. 重新执行慢开始；达到新门限后转入拥塞避免。

例如，`cwnd=16 MSS` 时发生超时，若题目规定门限取一半，则：

```text
ssthresh = 8 MSS
cwnd = 1 MSS
后续：1 → 2 → 4 → 8，之后线性增长
```

### 6.5 快重传与快恢复

发送方收到 3 个重复 ACK 后，立即重传推测丢失的报文段，这就是快重传。重复 ACK 说明部分后续报文仍能到达，网络通常没有像超时那样严重，因此 TCP Reno 不把 `cwnd` 直接降到 `1 MSS`，而是进入快恢复。

在经典的简化计算中，通常按以下方式处理：

1. `ssthresh` 减为发生拥塞时窗口的一半。
2. 执行快重传。
3. 快恢复结束后令 `cwnd` 回到新门限附近，直接进入拥塞避免。

更细化的 Reno 过程会在收到 3 个重复 ACK 时暂时令 `cwnd=ssthresh+3 MSS`，每多收到一个重复 ACK 再临时增加 `1 MSS`；当确认丢失数据的新 ACK 到达后，将 `cwnd` 调整为 `ssthresh` 并进入拥塞避免。若题目只采用教材简化模型，应按题目给出的窗口变化规则计算。

作为拓展了解，TCP Tahoe 没有快恢复，即使由 3 个重复 ACK 触发快重传，也会把 `cwnd` 降到较小初值并重新慢开始。题目明确给出 Tahoe 或 Reno 时，必须区分二者。

### 6.6 四种机制的关系

| 事件或阶段 | `cwnd` 的典型变化 | 后续阶段 |
| --- | --- | --- |
| 慢开始 | 每个 RTT 近似翻倍 | 达到 `ssthresh` 后进入拥塞避免 |
| 拥塞避免 | 每个 RTT 约增加 `1 MSS` | 继续线性增长 |
| 发生超时 | 门限减半，窗口降至较小初值 | 重新慢开始 |
| 3 个重复 ACK | 快重传；Reno 中窗口不降至最小 | 快恢复后进入拥塞避免 |

这种控制体现了“加法增大、乘法减小”的基本思想：网络正常时谨慎增加发送量，发现拥塞后显著降低发送量。

::: warning 易错点
`cwnd` 是发送方根据网络状况维护的变量，不通过 TCP 首部直接通告；`rwnd` 才由接收方在窗口字段中通告。超时与 3 个重复 ACK 的窗口处理不同，窗口题必须先确认题目采用的 TCP 版本和规则。
:::

::: tip 本节主线
TCP 首部中的序号、确认号和控制位支撑连接管理与可靠传输，接收窗口 `rwnd` 防止接收端溢出，拥塞窗口 `cwnd` 限制注入网络的数据量。实际发送能力由 `rwnd`、`cwnd` 和当前在途数据共同决定。
:::
