<h1><center>第二节 UDP</center></h1>

用户数据报协议 UDP 是 Internet 传输层的无连接协议。它以较小的协议开销向应用进程提供面向报文的尽最大努力交付服务。

## 1. UDP 数据报

### 1.1 UDP 的主要特点

1. **无连接**：发送数据前不建立连接，通信结束后也不需要释放连接。
2. **尽最大努力交付**：UDP 不确认、不重传，不保证数据一定到达，也不保证按序到达或只到达一次。
3. **面向报文**：UDP 对应用层交付的每个报文分别添加首部，并把它作为一个完整的用户数据报交给 IP 层。
4. **首部开销小**：UDP 首部固定为 8 B，只有四个字段。
5. **支持多种通信方式**：除一对一通信外，UDP 还可以配合 IP 广播或多播实现一对多、多对一和多对多通信。
6. **没有流量控制和拥塞控制**：UDP 不会根据接收方处理能力或网络拥塞程度自动调整发送速率。

UDP 虽然不提供可靠传输，但应用层可以根据需要自行增加序号、确认、重传、速率控制等机制。使用 UDP 的应用仍应合理控制发送速率，不能把“没有拥塞控制”理解为可以无节制地向网络发送数据。

### 1.2 UDP 数据报格式

UDP 数据报由 8 B 首部和数据部分组成。首部包含四个长度均为 16 bit 的字段：

```text
  0               15 16              31
 +------------------+------------------+
 |      源端口       |      目的端口      |
 +------------------+------------------+
 |      UDP 长度     |     UDP 检验和     |
 +------------------+------------------+
 |                数据                |
 +------------------------------------+
```

| 字段 | 长度 | 作用 |
| --- | --- | --- |
| 源端口 | 16 bit | 标识发送方应用的端口，便于接收方返回数据；不需要回复时可以填 0 |
| 目的端口 | 16 bit | 标识接收方应用的端口，接收端据此进行分用 |
| UDP 长度 | 16 bit | UDP 首部与数据部分的总长度，单位为字节 |
| UDP 检验和 | 16 bit | 检测伪首部、UDP 首部和数据中的比特差错 |

UDP 首部固定为 8 B，所以：

$$
\text{UDP 数据长度}=\text{UDP 长度字段值}-8\text{ B}.
$$

当 UDP 数据部分为空时，UDP 长度字段的最小值为 8。UDP 长度不包含 IP 首部，也不包含计算检验和时临时补上的填充字节。

### 1.3 面向报文

UDP 保留应用层报文的边界。发送方应用每交付一个报文，UDP 就生成一个用户数据报；接收方应用每次接收的仍是一个完整的 UDP 报文，而不是没有边界的连续字节流。

```text
应用报文 A ──→ UDP 数据报 A
应用报文 B ──→ UDP 数据报 B
```

UDP 本身不会把多个应用报文合并成一个 UDP 数据报，也不会把一个应用报文拆成多个 UDP 数据报。若 UDP 数据报超过下层网络能够直接承载的大小，可能由 IP 层进行分片；这属于网络层分片，不改变 UDP 面向报文的性质。

过大的 UDP 数据报会增加 IP 分片风险。只要一个分片丢失，接收端就无法重组出完整的 IP 数据报，因而整个 UDP 数据报都不能交付给应用进程。

### 1.4 复用、分用与适用场景

发送端 UDP 接收多个应用进程的数据，为其添加源端口和目的端口后交给 IP 层，这属于复用。接收端 UDP 主要根据目的 IP 地址和目的端口号找到相应套接字，把数据交付给正确应用，这属于分用。

UDP 适合以下场景：

- 请求和响应较简单，希望减少连接建立开销，如常见的 DNS 查询。
- 对实时性要求较高，少量数据丢失比等待重传更容易接受，如部分实时音视频业务。
- 需要广播或多播。
- 应用希望自行设计可靠传输或拥塞控制机制。

::: warning 易错点
UDP 无连接不等于没有端口，尽最大努力交付也不等于完全不检错。UDP 仍使用端口完成进程寻址，并可以使用检验和检测差错；它缺少的是确认、重传、按序交付等可靠传输机制。
:::

## 2. UDP 检验

### 2.1 UDP 检验和的范围

UDP 检验和的计算范围包括：

1. 根据网络层信息构造的伪首部。
2. UDP 首部，其中检验和字段在发送端计算时暂时置 0。
3. UDP 数据部分。

IPv4 环境中的 UDP 伪首部通常为 12 B：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| 源 IPv4 地址 | 32 bit | 取自 IPv4 首部 |
| 目的 IPv4 地址 | 32 bit | 取自 IPv4 首部 |
| 全 0 字段 | 8 bit | 补齐格式 |
| 协议号 | 8 bit | UDP 的协议号为 17 |
| UDP 长度 | 16 bit | 与 UDP 首部中的长度字段相同 |

伪首部不是 UDP 数据报真正传输的首部：它不向下交付给 IP 层，不在网络上传输，也不计入 UDP 长度。加入伪首部的目的，是让检验过程同时覆盖源、目的 IP 地址、上层协议号和 UDP 长度等关键信息，以发现部分误投递问题。

```text
仅参与计算：  伪首部
实际传输：    UDP 首部 + UDP 数据
检验范围：    伪首部 + UDP 首部 + UDP 数据
```

### 2.2 发送端的计算过程

UDP 检验和采用 16 bit 反码加法。发送端按以下步骤计算：

1. 构造伪首部，并把 UDP 首部中的检验和字段置为全 0。
2. 按顺序连接伪首部、UDP 首部和 UDP 数据。
3. 若总字节数为奇数，在末尾临时补一个全 0 字节，使其成为偶数字节。该字节只参与计算，不传输，也不计入 UDP 长度。
4. 把全部内容划分为若干个 16 bit 字，使用反码加法逐项相加。
5. 若最高位产生进位，把进位回卷到结果的最低位继续相加，这称为**回卷进位**。
6. 将最终和按位取反，结果写入 UDP 检验和字段。

设参加计算的 16 bit 字为 $W_1,W_2,\ldots,W_n$，则：

$$
\text{UDP 检验和}=\operatorname{NOT}(W_1\boxplus W_2\boxplus\cdots\boxplus W_n),
$$

其中 $\boxplus$ 表示带回卷进位的 16 bit 反码加法。

例如，只考虑两个 16 bit 字 `0xF123` 和 `0x2345`：

```text
普通相加：0xF123 + 0x2345 = 0x11468
回卷进位：0x1468 + 0x0001 = 0x1469
按位取反：UDP 检验和 = 0xEB96
```

### 2.3 接收端的检验过程

对于实际使用检验和的 UDP 数据报，接收端根据收到的 IP 数据报重新构造伪首部，把伪首部、收到的 UDP 首部和 UDP 数据按相同方法进行反码求和。此时 UDP 首部中的检验和字段也参加运算。

- 若最终结果为 16 bit 全 1，即 `0xFFFF`，表示未检测到差错，可以继续进行分用。
- 若结果不是全 1，表示检测到差错，该 UDP 数据报通常被丢弃。

检验结果正确只表示“没有检测到差错”，不能证明数据绝对正确。检验和属于检错机制，不能纠错，也不能提供确认、重传或可靠交付。

### 2.4 全 0 与全 1 的特殊含义

在 IPv4 中，UDP 检验和可以不使用。发送方若未计算检验和，就把检验和字段填写为 `0x0000`。

如果发送方实际计算得到的检验和恰好为 `0x0000`，则应在报文中发送 `0xFFFF`，避免与“未使用检验和”混淆。在反码运算中，这两种表示对求和结果具有相同作用。

在普通 IPv6 UDP 通信中，UDP 检验和必须使用，不能用全 0 表示省略。

::: tip 计算题步骤
先写伪首部，再把 UDP 检验和字段置 0；若总字节数为奇数，只为计算临时补 0；按 16 bit 分组做反码加法并回卷进位，最后按位取反。接收端把收到的检验和一起相加，结果应为全 1。
:::

::: tip 本节主线
UDP 以 8 B 固定首部提供无连接、面向报文的尽最大努力交付。它不负责确认和重传，但提供覆盖伪首部、UDP 首部及数据的检验和字段；使用该检验和时，可以检测传输差错。在 IPv4 中检验和可以省略，普通 IPv6 UDP 通信中则必须使用。
:::
