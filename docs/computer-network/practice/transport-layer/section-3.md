<h1><center>第三节 TCP</center></h1>

::: info 例 1
TCP 报文段序号为 1001，携带 500 字节数据。接收方正确收到后确认号是多少？
:::

::: details 解析
$$
ACK=1001+500=1501.
$$
表示接收方期待下一个字节序号 1501。
:::

::: info 例 2
发送方收到三个确认号均为 2001 的重复 ACK，通常采取什么动作？
:::

::: details 解析
执行快速重传，不等待计时器超时，立即重传从序号 2001 开始的推测丢失报文段，并按具体 TCP 版本进入快恢复或相应拥塞处理。
:::

::: info 例 3
TCP 为什么需要序号，即使已有校验和？
:::

::: details 解析
校验和只能检测比特错误；序号还能识别丢失、重复与乱序，并使接收方能够按序重组字节流。
:::

::: info 例 4
接收窗口 `rwnd` 为 $12\text{ KB}$，拥塞窗口 `cwnd` 为 $8\text{ KB}$，未确认数据为 $3\text{ KB}$，还能继续发送多少？
:::

::: details 解析
实际窗口为：
$$
\min(12,8)=8\text{ KB}.
$$
已有 $3\text{ KB}$ 在途，因此还可以发送 $8-3=5\text{ KB}$。
:::

::: info 例 5
`cwnd` 初始为 1 MSS，慢开始期间无丢包，经过 4 个 RTT 后约为多少？
:::

::: details 解析
按每个 RTT 近似翻倍：
$$
1\rightarrow2\rightarrow4\rightarrow8\rightarrow16\text{ MSS}.
$$
前提是没有提前达到 `ssthresh`。
:::

::: info 例 6
接收方通告零窗口后，窗口更新报文丢失，TCP 如何避免永久等待？
:::

::: details 解析
发送方启动持续计时器，超时后发送零窗口探测，促使接收方重新通告当前接收窗口。
:::

::: info 例 7
客户端第一次握手序号为 100，服务器第二次握手序号为 500，写出第二、三次握手的确认号。
:::

::: details 解析
SYN 消耗一个序号：

- 第二次握手：`ack=101`。
- 第三次握手：`ack=501`，客户端自身序号从 101 开始。
:::

::: info 例 8
为什么 TCP 关闭通常需要四次交互？
:::

::: details 解析
TCP 是全双工的，每个方向的数据流需要独立关闭。收到对方 FIN 只能确认该方向关闭，本方可能仍有数据，因此 ACK 和本方 FIN 通常分开发送。
:::

::: info 例 9
主动关闭方为什么等待 $2MSL$？
:::

::: details 解析
一是保证最后 ACK 丢失时能够重新发送；二是让旧连接中滞留的重复报文在网络中消失，避免影响相同四元组的新连接。
:::

::: info 例 10
发送方从序号 3000 开始连续发送三个各含 1000 字节数据的报文段。第二段丢失、第三段到达，接收方通常返回什么确认号？
:::

::: details 解析
第一段覆盖 3000～3999，接收方期待 4000。第二段丢失造成字节流空洞，因此即使第三段到达，累计确认通常仍为：
$$
ACK=4000.
$$
:::

## 答题技巧

- TCP 序号按数据字节数推进，SYN 和 FIN 额外各消耗一个序号。
- 窗口题先取 `min(rwnd, cwnd)`，再减去在途未确认数据。
- 握手和挥手题逐个报文写出控制位、`seq` 与 `ack`。
