<h1><center>第二节 CPU 调度</center></h1>

## 1. 调度的概念

调度是操作系统按一定策略分配处理器、内存和 I/O 等资源的过程。按作用层次可分为：

| 层次 | 又称 | 主要任务 | 特点 |
| --- | --- | --- | --- |
| 高级调度 | 作业调度 | 从外存后备队列选择作业进入内存 | 决定系统并发度，频率较低 |
| 中级调度 | 内存调度 | 挂起或激活进程，调整内存中的进程数量 | 缓解内存紧张，提高内存利用率 |
| 低级调度 | 进程 / CPU 调度 | 从就绪队列选择执行实体占用处理器 | 发生最频繁，直接决定下一个运行者 |

本节的 CPU 调度通常指低级调度。现代系统的实际调度对象往往是内核级线程；若进程只有一个线程，则可将其视为调度对象。

调度可分为两类：

- **非抢占式调度**：一旦进程获得 CPU，除非它主动阻塞或终止，否则继续运行。
- **抢占式调度**：时间片用完或更高优先级进程到达时，系统可收回 CPU 并重新调度。

## 2. 进程调度

进程调度从就绪队列中选择一个进程（或线程）投入运行。调度程序通常在以下时机被触发：

1. 运行进程终止。
2. 运行进程因 I/O 请求、等待资源等原因进入阻塞态。
3. I/O 完成等事件使阻塞进程转入就绪态。
4. 时钟中断使时间片用完，或有更高优先级进程到达。

前两种情形中当前进程主动放弃 CPU；后两种情形是否发生调度和抢占取决于系统策略。抢占式调度响应更快，适合分时和实时场景，但会增加切换开销。

即使产生了调度请求，内核在以下关键阶段通常也不能立即进行进程切换：

- 正在处理中断，且中断现场尚未保存或恢复完毕。
- 正在执行必须保持原子性的操作。
- 正在访问需要互斥保护的内核临界数据结构。

内核会先记录调度请求，待退出关键阶段、到达安全的调度点后再执行切换。处于普通用户态执行、系统调用完成返回前或中断处理结束时，若调度条件满足，则可以进行调度。

调度相关的主要组成如下：

- **调度器**：维护就绪队列，依照调度算法选出下一个运行实体。
- **分派程序**：执行上下文切换，将 CPU 控制权交给被选中的实体。
- **闲逛进程**：没有普通就绪任务时运行；它不参与普通任务竞争，常用于降低功耗或等待中断。

## 3. 调度的目标

不同系统的调度目标不同：批处理系统重视吞吐量和周转时间，交互式系统重视响应时间，实时系统重视在截止时间前完成任务。

| 指标 | 含义 | 一般目标 |
| --- | --- | --- |
| CPU 利用率 | CPU 忙于有效工作的比例 | 高 |
| 吞吐量 | 单位时间完成的作业数 | 高 |
| 周转时间 | 完成时间 − 到达时间 | 低 |
| 带权周转时间 | 周转时间 ÷ 服务时间 | 低 |
| 等待时间 | 在就绪队列中的累计等待时间 | 低 |
| 响应时间 | 首次得到 CPU 的时间 − 到达时间 | 低 |
| 公平性 | 进程获得服务的合理程度 | 避免长期饥饿 |

$$
\text{周转时间}=\text{完成时间}-\text{到达时间}
$$

$$
\text{带权周转时间}=\frac{\text{周转时间}}{\text{服务时间}}
$$

$$
\text{等待时间}=\text{周转时间}-\text{服务时间}
$$

上式只适用于不计 I/O 或其他阻塞时间的简化调度模型。一般情况下，等待时间是进程在就绪队列中的累计时间，不能直接用“周转时间减服务时间”计算。

一个调度策略通常无法同时使所有指标最优，因此需要根据系统类型权衡。例如，过小的时间片可改善响应性，却会使上下文切换过于频繁。

## 4. 进程切换

进程切换（上下文切换）是 CPU 从一个执行实体转而执行另一个执行实体的过程。内核通常需要：

1. 保存当前实体的程序计数器、寄存器、栈指针等处理器现场。
2. 更新其 PCB 或 TCB 中的状态和队列位置。
3. 选择下一个就绪实体，必要时切换页表或地址空间。
4. 恢复下一个实体的上下文，并从保存的位置继续执行。

上下文切换本身不推进任何用户任务，还会影响高速缓存和 TLB 的有效内容，因此属于调度开销。同一进程内的线程切换通常不必更换地址空间，代价一般小于进程切换。

::: tip 区分模式切换与进程切换
用户态进入内核态（如执行系统调用）是模式切换，不一定更换执行实体；进程切换一定需要内核参与，但不一定由一次系统调用直接引起。
:::

## 5. CPU 调度算法

### 5.1 先来先服务（FCFS）

按进程到达就绪队列的先后顺序调度，通常为非抢占式。实现简单，但长作业可能使短作业长时间等待，形成**护航效应**。

### 5.2 短作业优先（SJF）

SJF 每次选择**估计服务时间最短**的就绪作业，属于非抢占式算法：作业一旦开始运行，就一直运行到完成或主动放弃 CPU。

在作业同时到达的简化模型中，SJF 能得到最小的平均等待时间和平均周转时间；但实际系统只能**估计**服务时间，估计偏差会直接影响调度效果。长作业在持续到达的短作业面前可能长期得不到调度，即**饥饿**。

### 5.3 最短剩余时间优先（SRTF）

SRTF 是 SJF 的抢占式版本：新作业到达时，若其服务时间短于当前作业的**剩余运行时间**，则立即抢占，被抢占的作业回到就绪队列等待。

抢占只会发生在作业到达时刻，因此画甘特图时应逐个到达时刻比较剩余时间。SRTF 的平均等待时间通常比 SJF 更短，但抢占频繁、上下文切换开销更大，并且同样依赖服务时间的估计，同样可能使长作业饥饿。

### 5.4 高响应比优先（HRRN）

HRRN 每次选择响应比最高的作业：

$$
R_p=\frac{\text{等待时间}+\text{服务时间}}{\text{服务时间}}
=1+\frac{\text{等待时间}}{\text{服务时间}}.
$$

等待时间越长，响应比越高，因此它在照顾短作业的同时能缓解长作业饥饿；通常采用非抢占方式。

### 5.5 时间片轮转（RR）

每个就绪进程最多运行一个时间片；时间片结束且尚未完成时，进程被放回就绪队列尾部。RR 公平且响应较好，适用于分时系统。时间片过大时接近 FCFS，过小时切换开销过高。

### 5.6 优先级调度算法

为每个进程设置优先级，调度时选择优先级最高的就绪进程。若更高优先级进程到达时立即抢占当前进程，则为抢占式；否则为非抢占式。

同优先级的进程可按 FCFS 或 RR 调度。优先级数值的大小与优先程度的对应关系由系统规定，做题时不能默认“数值越大，优先级越高”。

| 优先级类型 | 确定方式 | 特点 |
| --- | --- | --- |
| 静态优先级 | 创建进程时确定，运行期间保持不变 | 实现简单，但不能随进程行为变化而调整 |
| 动态优先级 | 根据等待时间、已用 CPU 时间等因素调整 | 可随等待时间增加而提高，或随 CPU 使用量增加而降低 |

常见的设置原则包括：系统进程高于用户进程，交互型高于计算型，I/O 繁忙型高于 CPU 繁忙型。这些是设计时的参考，并非所有系统都必须遵循。让 I/O 繁忙的进程尽快获得 CPU 去启动 I/O，有利于设备与 CPU 并行工作。在非抢占方式下，若按估计服务时间越短、优先级越高的规则选择进程，就得到 SJF。

优先级调度的主要问题是**饥饿**：不断到达的高优先级进程会让低优先级进程无限期等待，可用**老化**（随等待时间增加而提升优先级）缓解。

### 5.7 多级队列调度算法

按进程性质把就绪队列划分为若干**固定**队列，例如系统进程队列、交互队列、批处理队列。调度时需要分别确定**队列之间如何分配 CPU**和**队列内部如何选择进程**；例如交互队列采用 RR，批处理队列采用 FCFS。队列之间的关系有两种安排：

| 队列间规则 | 做法 | 特点 |
| --- | --- | --- |
| 固定优先级 | 高优先级队列全空时才调度低优先级队列 | 实现简单，低优先级队列可能饥饿 |
| 按比例划分时间 | 各队列按预设比例分享 CPU，如前台 80%、后台 20% | 为各队列保留服务份额，但队列内是否饥饿仍取决于内部算法 |

进程在创建时被确定所属队列，**通常不允许在队列之间移动**，这是它与多级反馈队列最本质的区别。

### 5.8 多级反馈队列（MLFQ）

设置多个优先级递减的队列，通常优先级越高时间片越短，并允许进程在队列间移动。一种基本规则如下：

1. 新进程进入最高优先级队列的队尾，按该级时间片运行。
2. 时间片用完仍未完成，则降到下一级队列的队尾；已在最低级队列的进程按时间片轮转。
3. 若进程在时间片内因等待 I/O 等事件主动放弃 CPU，则进入阻塞态；I/O 完成后，可按规则回到原优先级队列。

只有在高优先级队列为空时才会调度低优先级队列；高优先级队列一旦有新进程到达，可立即抢占当前进程。它无须预知服务时间，能同时照顾短任务、交互任务和长任务，是通用系统的常用方案；代价是队列数、各级时间片和升降级规则等参数需要仔细设计，长任务在极端情况下仍可能被不断到达的短任务压制。

为缓解饥饿，可定期把进程提升到高优先级队列；为防止进程通过频繁主动让出 CPU 逃避降级，也可累计其在本级使用的 CPU 时间，用完本级配额后再降级。具体升降级规则以题目或系统实现为准。

| 比较项 | 多级队列 | 多级反馈队列 |
| --- | --- | --- |
| 队列归属 | 通常按进程类别固定分配 | 随运行行为和等待情况调整 |
| 队列间迁移 | 通常不允许 | 允许，是“反馈”的体现 |
| 主要用途 | 对不同类别的进程采用不同策略 | 根据实际行为兼顾响应性与吞吐量 |

### 5.9 基于公平原则的调度算法

**公平原则**类算法关注进程、用户或进程组是否获得了约定的 CPU 份额，常用于多用户分时系统。公平不一定意味着平均分配，也可以按预设权重分配。

#### 5.9.1 保证调度

系统跟踪各进程实际获得的 CPU 时间，并优先补偿获得服务不足的进程。在单 CPU、忽略调度开销、$n$ 个进程持续竞争且权重相同的简化模型中，经过时间 $t$ 后，每个进程应得的 CPU 时间为 $t/n$。

$$
R_i=\frac{\text{进程 }i\text{ 实际获得的 CPU 时间}}{\text{进程 }i\text{ 应得的 CPU 时间}}
$$

调度时优先选择比值 $R_i$ 最小的就绪进程，使实际分配逐渐接近应得份额。若参与竞争的进程数发生变化，应分段更新应得时间，不能始终使用同一个 $n$。这里保证的是处理器服务份额，不是作业在某个截止时间前完成。

#### 5.9.2 彩票调度

给每个进程分配若干张彩票，每次调度从可运行进程持有的彩票中随机抽取一张，中奖进程获得 CPU。持有的彩票越多，被选中的概率越高：

$$
P_i=\frac{\text{进程 }i\text{ 持有的彩票数}}{\text{所有可运行进程持有的彩票总数}}
$$

例如，两个持续就绪的进程分别持有 20 张和 80 张彩票；若每次运行相同长度的时间片，则长期 CPU 份额趋近于 20% 和 80%。短期分配可能明显偏离这一比例，即使持有彩票，也不能保证在固定次数的抽签内获选。因此，彩票调度提供的是**统计意义上的公平**，不保证等待时间上界。参见 [OSTEP：比例共享调度](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched-lottery.pdf)。

#### 5.9.3 公平分享调度

以**用户或进程组**为单位分配 CPU 份额，再在组内分配给各进程，并根据实际 CPU 使用量调整调度。各用户可以具有相同或不同的权重；同一用户多创建进程，不应因此扩大其整体份额。

例如，用户 A、B 的份额各为 50%，A 有 1 个进程，B 有 3 个进程，且所有进程持续就绪。若组内平均分配，则 A 的进程获得约 50% 的 CPU 时间，B 的每个进程获得约 $50\%/3$，而不是四个进程各占 25%。

这类算法以长期份额公平为主要目标，并不以最小平均周转时间为目标，也不能仅凭份额分配保证实时任务的截止时间。


## 6. 多处理机调度

多处理机调度需要在提高并行度、维持负载均衡和利用缓存局部性之间权衡。

- **对称多处理（SMP）**：多个处理器地位相同，都可执行内核代码并参与调度，是现代通用系统的常见形式。
- **非对称多处理（AMP）**：一个主处理器负责调度等系统任务，其他处理器执行分配的工作，管理较简单但主处理器可能成为瓶颈。

就绪队列组织有两种典型方式：

| 方式 | 优点 | 挑战 |
| --- | --- | --- |
| 公共就绪队列 | 所有处理器都可取任务，天然利于均衡负载 | 队列锁竞争较明显 |
| 每处理器私有队列 | 本地访问快，缓存局部性好 | 可能负载不均，需要任务迁移 |

**处理器亲和性**是尽量让任务继续在原处理器上运行，以保留其高速缓存内容；**负载均衡**则通过迁移任务避免部分处理器空闲。实际系统需要在两者之间折中，并在必要时迁移任务。
