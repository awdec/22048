<h1><center>第四节 死锁</center></h1>

死锁是并发系统中的资源分配问题。本节依次讨论死锁的形成条件，以及预防、避免、检测和解除四类处理思路。

## 1. 死锁的概念

### 1.1 死锁的定义

多个进程因竞争资源而相互等待，若没有外力干预，这些进程都将永远无法继续推进，这种状态称为**死锁**。

例如，进程 $P_1$ 已持有资源 $R_1$ 并等待 $R_2$，进程 $P_2$ 已持有 $R_2$ 并等待 $R_1$，二者都无法主动释放当前资源，于是形成死锁。

```mermaid
flowchart LR
    P1["进程 P1"] -->|"请求"| R2["资源 R2"]
    R2 -->|"已分配"| P2["进程 P2"]
    P2 -->|"请求"| R1["资源 R1"]
    R1 -->|"已分配"| P1
```

### 1.2 死锁产生的原因

死锁通常由两方面共同引起：

- **资源竞争**：不可剥夺资源的数量不足，多个进程无法同时满足全部需求。
- **推进顺序不当**：进程以不合理的顺序申请和保持资源，形成相互等待。

可重复使用的资源，如锁、文件和设备，使用后能够释放；消耗性资源，如消息和信号，只会被产生和消费。两类资源使用不当都可能造成死锁。

### 1.3 死锁的四个必要条件

死锁发生时，以下四个条件必然同时成立：

1. **互斥条件**：资源在一段时间内只能由一个进程占用。
2. **不剥夺条件**：进程已获得的资源在使用完之前不能被强制夺走，只能主动释放。
3. **请求并保持条件**：进程保持已有资源的同时，又申请新的资源。
4. **循环等待条件**：存在进程—资源的首尾相接循环等待链。

四个条件是死锁的必要条件而非任一单独的充分条件。破坏其中任何一个条件，死锁都不可能发生。

### 1.4 死锁、饥饿与活锁

| 现象 | 主要表现 | 其他进程能否推进 |
| --- | --- | --- |
| 死锁 | 一组进程互相等待，均无法推进 | 死锁组外的进程可能推进 |
| 饥饿 | 某进程长期得不到资源或调度机会 | 通常可以 |
| 活锁 | 进程不断改变状态或重试，却没有实际进展 | 相关进程持续活动但不完成 |

## 2. 死锁预防

死锁预防通过系统规则破坏至少一个必要条件，使系统从结构上不可能发生死锁。

| 被破坏的条件 | 预防方法 | 局限 |
| --- | --- | --- |
| 互斥条件 | 将独占资源改造为可共享资源，如使用假脱机技术共享打印机 | 许多资源本质上不能同时共享 |
| 不剥夺条件 | 新资源申请失败时释放已有资源，或由系统剥夺资源 | 只适合状态易保存、易恢复的资源 |
| 请求并保持条件 | 运行前一次性申请全部资源，或仅在不持有资源时申请 | 资源利用率低，可能导致饥饿 |
| 循环等待条件 | 为资源统一编号，规定进程只能按编号递增顺序申请 | 编号困难，申请顺序受限，使用不灵活 |

预防方法实现直接，不需要掌握进程未来的最大需求，但限制通常较强，可能降低资源利用率和系统并发度。

::: tip 有序资源分配法
若所有进程都只能按资源编号递增顺序申请，就不可能出现编号沿等待链不断递增后又回到较小编号的闭环，因此破坏了循环等待条件。
:::

## 3. 死锁避免

死锁避免不预先破坏必要条件，而是在每次分配资源前预测分配结果，只允许系统保持在**安全状态**。

### 3.1 安全状态与安全序列

若系统能够找到一个进程序列 $\langle P_1,P_2,\ldots,P_n\rangle$，使每个进程所需的剩余资源都能由“当前可用资源加上前面进程完成后释放的资源”满足，则该序列称为**安全序列**，系统处于安全状态。

$$
\text{安全状态}\Rightarrow\text{没有死锁}
$$

$$
\text{死锁状态}\Rightarrow\text{不安全状态}
$$

不安全状态不等于已经死锁，但系统已无法保证所有进程都能完成，之后可能进入死锁。

### 3.2 银行家算法的数据结构

设系统有 $n$ 个进程、$m$ 类资源：

| 数据结构 | 含义 |
| --- | --- |
| `Available[m]` | 每类资源当前可用数量 |
| `Max[n][m]` | 每个进程对各类资源的最大需求 |
| `Allocation[n][m]` | 当前已分配给各进程的资源 |
| `Need[n][m]` | 各进程尚需资源，`Need = Max - Allocation` |

进程 $P_i$ 提出请求 `Requestᵢ` 时，依次检查：

1. `Requestᵢ ≤ Needᵢ`，否则说明请求超过其声明的最大需求。
2. `Requestᵢ ≤ Available`，否则让进程等待。
3. 假定分配并更新 `Available`、`Allocationᵢ`、`Needᵢ`。
4. 执行安全性算法；若安全则正式分配，否则撤销试分配并让进程等待。

安全性算法令 `Work=Available`，反复寻找尚未完成且满足 `Needᵢ ≤ Work` 的进程。假定它完成并执行：

```text
Work = Work + Allocation[i]
Finish[i] = true
```

若最终所有 `Finish[i]` 都为真，则系统安全；找到进程的先后次序就是一个安全序列。

### 3.3 资源分配图

资源分配图中的节点表示进程和资源：

- 进程指向资源的边表示**请求边**。
- 资源实例指向进程的边表示**分配边**。

每类资源只有一个实例时，图中存在环是死锁的充分必要条件；某类资源存在多个实例时，图中有环仅表示可能死锁，还需结合可用资源数和剩余请求判断。

::: warning 易错点
银行家算法属于死锁避免：它在资源正式分配前执行安全性检查。它不是用来判断当前已经有哪些进程死锁的检测算法。
:::

## 4. 死锁检测与解除

死锁检测策略允许系统进入死锁，再通过检测算法识别死锁进程，随后解除死锁。它适合死锁发生概率较低、预防或避免代价较高的系统。

### 4.1 死锁检测

对于每类只有一个实例的资源，可使用**等待图**：删除资源节点后，若 $P_i$ 等待 $P_j$ 所占资源，则建立 $P_i\rightarrow P_j$。等待图存在环即说明发生死锁。

对于多实例资源，检测算法使用：

- `Available`：当前可用资源。
- `Allocation`：各进程已占有的资源。
- `Request`：各进程当前尚未满足的请求。

令 `Work=Available`，反复查找满足 `Requestᵢ ≤ Work` 的进程，假定它完成后将 `Allocationᵢ` 加回 `Work`。算法结束时仍无法标记完成且占有资源的进程构成死锁集合。

检测开始时应正确初始化完成标记：

```text
Work = Available

for each process Pi:
    if Allocation[i] == 0:
        Finish[i] = true
    else:
        Finish[i] = false
```

随后反复查找同时满足以下条件的进程：

```text
Finish[i] == false
Request[i] <= Work
```

找到后假定该进程能够完成，执行：

```text
Work = Work + Allocation[i]
Finish[i] = true
```

算法结束时，所有满足 `Finish[i] == false` 的进程构成死锁集合。这里的 `Request` 表示当前尚未满足的实际请求，不是银行家算法中根据最大需求计算的 `Need`。

检测频率需要权衡：检测过于频繁会增加系统开销；间隔过长则可能使更多进程卷入死锁、解除代价增大。

### 4.2 死锁解除

检测到死锁后，可采用以下方法：

1. **终止进程**：一次终止全部死锁进程，或逐个终止直到环被打破。
2. **资源剥夺**：从部分进程处强制收回资源，分配给其他死锁进程。
3. **进程回退**：将进程恢复到之前的安全检查点，释放资源后重新执行。

选择牺牲进程或剥夺对象时，应综合考虑：

- 进程优先级和重要性。
- 已执行时间与剩余工作量。
- 已占有及仍需资源的数量。
- 回退、重启和数据恢复代价。
- 该进程此前被选作牺牲者的次数，避免长期饥饿。

| 策略 | 核心思想 | 是否允许死锁发生 |
| --- | --- | --- |
| 预防 | 破坏必要条件 | 否 |
| 避免 | 只进入安全状态 | 否 |
| 检测与解除 | 先检测，再终止、剥夺或回退 | 是 |
