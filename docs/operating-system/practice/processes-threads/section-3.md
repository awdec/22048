<h1><center>第三节 同步与互斥</center></h1>

::: info 例 1：同步与互斥
生产者向缓冲区放入数据后，消费者才能取走数据；多个生产者不能同时修改缓冲区。这两种约束分别属于同步还是互斥？
:::

::: details 解析
“先放入、后取走”规定了执行先后次序，属于同步；“不能同时修改缓冲区”要求排他访问临界资源，属于互斥。一个并发问题可以同时包含同步和互斥关系。
:::

::: info 例 2：临界区原则
某算法能保证两个进程不会同时进入临界区，但规定它们必须严格轮流进入。即使 $P_1$ 不想进入，$P_0$ 连续使用一次后也必须等待 $P_1$。该算法违反了什么原则？
:::

::: details 解析
违反**空闲让进**。临界区空闲且只有 $P_0$ 申请时，本应允许它立即进入；严格轮流会使空闲临界区无人使用。
:::

::: info 例 3：Peterson 算法
Peterson 算法中的 `flag[i]` 和 `turn` 分别起什么作用？它是否满足让权等待？
:::

::: details 解析
`flag[i]` 表示进程 $P_i$ 有进入临界区的意愿；`turn` 在双方同时申请时表示当前把机会让给谁。经典模型下该算法满足互斥、空闲让进和有限等待，但等待者会在循环中持续检查条件，属于忙等待，不满足让权等待。
:::

::: info 例 4：硬件方法
为什么关闭中断不能单独解决多处理器系统中的临界区互斥？
:::

::: details 解析
关闭当前处理器的中断只能避免当前处理器发生调度，其他处理器仍可同时执行并访问共享数据。多处理器互斥需要使用能在处理器之间保持原子性的指令或锁。
:::

::: info 例 5：互斥锁
自旋锁和阻塞式互斥锁分别适合什么等待场景？
:::

::: details 解析
自旋锁等待时持续占用 CPU，适合多核系统中临界区很短、预计很快解锁或线程不能睡眠的场景。阻塞式互斥锁会使等待线程休眠，适合等待时间较长的场景，但阻塞和唤醒会产生切换开销。
:::

::: info 例 6：同步信号量
进程 $P_1$ 的语句 A 必须先于 $P_2$ 的语句 B，写出信号量操作。
:::

::: details 解析
设同步信号量 `S=0`：

```text
P1: A; signal(S)
P2: wait(S); B
```

若 $P_2$ 先运行，它会在 `S` 上阻塞，直到 $P_1$ 完成 A 并执行 `signal(S)`。
:::

::: info 例 7：记录型信号量
记录型信号量 $S$ 的值为 $-3$，通常表示什么？随后连续执行两次 `signal(S)` 会产生什么效果？
:::

::: details 解析
通常表示有 3 个进程在该信号量的等待队列中。每次 `signal` 都使信号量加 1，并唤醒一个等待进程；两次后 $S=-1$，共唤醒 2 个进程，仍有 1 个进程等待。
:::

::: info 例 8：生产者—消费者
有界缓冲区容量为 $5$，如何初始化 `empty`、`full` 和 `mutex`？生产者为什么不能先执行 `wait(mutex)` 再执行 `wait(empty)`？
:::

::: details 解析
$$
empty=5,\qquad full=0,\qquad mutex=1.
$$

若缓冲区已满，生产者取得 `mutex` 后会在 `empty` 上阻塞；消费者必须取得 `mutex` 才能取走产品并增加 `empty`，却因锁被占用而无法进入，双方形成死锁。
:::

::: info 例 9：读者—写者
用信号量写出读者优先方案，并说明它为什么可能使写者饥饿。
:::

::: details 解析
设 `rw=1` 保证写者与其他访问者互斥，`mutex=1` 保护读者计数 `readCount=0`：

```text
reader:
    wait(mutex)
    readCount++
    if readCount == 1: wait(rw)
    signal(mutex)

    读

    wait(mutex)
    readCount--
    if readCount == 0: signal(rw)
    signal(mutex)

writer:
    wait(rw)
    写
    signal(rw)
```

第一个读者锁住共享文件，最后一个读者释放它。若读者持续到达，使 `readCount` 长期不为 0，等待 `rw` 的写者就可能一直得不到执行。
:::

::: info 例 10：哲学家进餐
五位哲学家共享五支筷子。设置计数信号量 `room=4`，每人进入取筷阶段前执行 `wait(room)`，为什么能避免死锁？是否自动保证无饥饿？
:::

::: details 解析
最多只有 4 人同时取筷子，不会形成 5 人各持一支筷子的完整循环等待；至少有一位哲学家能取得两支筷子并释放资源。因此该方法能避免死锁。

但若 `room` 或筷子锁的唤醒策略不公平，某人仍可能反复被其他人抢先，所以避免死锁并不自动保证无饥饿。
:::

::: info 例 11：管程与条件变量
条件变量的 `wait` 为什么必须原子地释放管程互斥权？被唤醒后为什么通常要用 `while` 重新检查条件？
:::

::: details 解析
若等待者不释放互斥权，其他线程无法进入管程改变共享状态，等待条件永远不能成立。线程被唤醒到重新获得管程互斥权之间，共享状态可能再次变化，也可能发生虚假唤醒，因此应使用 `while` 重新检查条件。
:::

::: info 例 12：信号量与条件变量
信号量执行 `signal` 时无人等待，与条件变量执行 `signal` 时无人等待，结果有什么不同？
:::

::: details 解析
信号量会增加计数，许可可由后续的 `wait` 使用；条件变量通常不保存这次通知，无人等待时 `signal` 不产生后续效果。条件变量必须配合共享状态判断条件是否成立。
:::

::: info 例 13：前驱图同步
语句 $S_1$ 与 $S_2$ 可以并发执行；二者都完成后才能执行 $S_3$；$S_3$ 完成后，$S_4$ 与 $S_5$ 才能并发执行。使用信号量描述这些前驱关系。
:::

::: details 解析
设置四个初值均为 0 的同步信号量 `a`、`b`、`c`、`d`：

```text
P1: S1; signal(a)
P2: S2; signal(b)

P3: wait(a); wait(b); S3; signal(c); signal(d)

P4: wait(c); S4
P5: wait(d); S5
```

汇合点 $S_3$ 需要分别等待 $S_1$、$S_2$ 的完成信号；分支点 $S_3$ 之后需要分别通知 $S_4$、$S_5$，不能只执行一次 `signal`。
:::

::: info 例 14：写者优先
写者优先读者—写者方案中，第一个等待写者为什么要关闭读者入口，而最后一个写者才重新开放？
:::

::: details 解析
第一个写者关闭读者入口后，新读者不能继续加入，现有读者退出后写者就能获得共享资源。若每个写者结束后都立即开放入口，连续到来的读者可能再次抢在其他等待写者前面。最后一个写者离开时再开放入口，可以维持写者优先；但持续到来的写者也可能使读者长期等待。
:::

::: info 例 15：吸烟者问题
吸烟者问题中为什么供应者放置一组材料后必须等待 `done`，不能立即继续放置下一组？
:::

::: details 解析
桌面一次只容纳一组材料。供应者若不等待，可能在上一组尚未被取走时覆盖或混入下一组，使多个吸烟者的同步条件混乱。吸烟者完成后执行 `signal(done)`，保证“放置一组—取走并吸烟—再放下一组”的循环次序。
:::
